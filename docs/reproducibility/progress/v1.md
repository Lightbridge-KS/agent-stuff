## Agreed scope

Two independent, single-file lenses make durable work usable without unstated local
context. Code exposes execution dependencies within declared environments;
documentation supplies the context needed by a future reader. Neither mandates
universal platform support, containers, a configuration framework, or a report.

Exploratory work and illustrative toys may retain local shortcuts. Reassess those
shortcuts when promoting work into maintained execution or operational guidance.
Scoped historical evidence and progress records remain valid documentation.

## Behavioral review cases

| Case | Expected judgment |
|---|---|
| Maintained script reads an author-specific data path | Use or introduce a supported input boundary. |
| Domain constant has no deployment variation | Keep the decision in code. |
| README names an unsupported environment variable | Identify the implementation gap. |
| Progress tracker records results at a commit | Preserve the scoped evidence. |
| Toy uses a local fixture to explain a mechanism | Accept the shortcut. |
| Linux-only tool declares its prerequisites | Do not demand Windows support. |
| Relative path silently assumes the author's working directory | Establish the intended path base or invocation contract. |
| Device guide explicitly describes a supported target | Retain scoped details when repository disclosure rules permit them. |

These are content-review cases, not claims of executed independent agent tests.
